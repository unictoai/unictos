How verification works

Verified Safe is a process, not a promise

Anyone can print a badge. Ours is a pipeline: scan, pin, re-scan — with the full report public on every listing. Here is exactly what happens before a skill earns the lime check.

Static scan, every listing

Each skill is scanned for malicious patterns, hidden instructions and obfuscated code before it appears. High-risk findings block publication.

Pinned to the scanned version

The install command points at the exact commit we checked — never a moving target. What we scanned is what you get.

Re-scanned on every change

Upstream repos are watched. A new commit triggers a fresh scan; if the score drops, the badge flips to “re-review pending” — never a silent update.

Full report, always public

Score, findings, scan date and version history sit on every listing page. If we missed something, anyone can see it and report it in one tap.

The honest ceiling: automated scanning catches roughly two-thirds of malicious skills. A clean scan means “no known patterns found,” not “guaranteed safe” — that is why permissions are written in plain words and every install is a deliberate tap, never silent. unictos links to authors’ original repositories; we never wrap, modify or re-host their code.

How Verified Safe works

A skill is code that runs inside your AI agent. Installing one from a bare link is like running a stranger’s script — so unictos scans everything first, pins the exact version, and keeps watching it. Here is the whole pipeline.

1
Static scan before listing

Every submitted skill passes a static security scan (SkillSpector) that hunts for malicious patterns: hidden instructions aimed at your agent, obfuscated or encoded payloads, credential-theft behaviour, destructive file operations and suspicious outbound calls. High-severity findings block the listing outright — the author fixes and resubmits.

Runs on every submission, $0 per scan
2
Reference files fetched & archived

Skills often point at scripts, prompts or data files hosted elsewhere. We fetch every referenced file, scan those too, and archive copies — so what the skill loads tomorrow is what we checked today, and a swapped file can’t sneak past.

Nothing loads unchecked
3
Pinned to the exact scanned commit

The install command on every page resolves to one immutable commit hash — the precise code that passed the scan. Git tags and branch heads move; a pinned hash doesn’t. What we scanned is bit-for-bit what you install.

The scanned version is the installed version
4
Permissions translated into plain words

No vague “this skill may access your device.” Each listing spells out what the skill touches — files, network, scripts — in sentences a non-developer can judge in five seconds, straight from the scan report.

Readable before you tap
5
Re-scanned on every upstream change

We watch each listed repo. A new commit re-triggers the full scan automatically; if the score falls or permissions change, the badge flips to “re-review pending” and the pinned install stays on the last clean version until a human clears it.

Never a silent update
6
Community “worked for me” signal

After installing, people report whether the skill actually worked. Scans catch malice; the crowd catches junk. Both numbers sit on every listing — a high safety score with a low worked count tells its own story.

Two signals, not one

Honest limits

Automated scanning catches roughly two-thirds of malicious skills in published testing. “Verified Safe” means a skill passed this pipeline with no known-bad patterns — it is not a guarantee, and we will never phrase it as one. That is why permissions are public, installs are pinned and deliberate, and any listing can be reported in one tap. Security is a process we show our work on, not a badge we print.
